Connecting an MCP client offers a choice of what to connect as. The OAuth consent step shows **Connect as** before the person approves: **Everything** (selected by default, and exactly the surface every connection had until now) or one of the agent configurations the distribution offers, by name with its description. Creating a connection key on the External agent access page offers the same choice. The choice is stored on the connection (`agent_connections.agent_path`) and on the key (`api_tokens.agent_path`), null being Everything (migration `0023_agent_path`, which also carries the choice on `oauth_auth_codes` from Finish to the token exchange), and is shown beside each key and in the Audit log's rows.

**Core owns the mechanism and no configuration.** What an agent configuration is — the file kind, where it lives, what its definition says — is the distribution's: `CorePorts.agentScope` makes its `IAgentScopeResolver` (`listChoices`, `choosable`, `resolve`) — a factory core calls once, during construction, with the CONTRACTS of the services a resolver reads through (`AgentScopeCollaborators`: `IWorkspaceService`, `IAccessControl`, `KbContext`, `ITreeWalker` and the plugins module's new `IPluginLinkIndex`, which `PluginLinkIndex` implements), so the one resolver reaches every surface, tool contexts and routes alike, and a resolver written against them runs on any implementation of them — and core's default, `noAgentConfigurations()`, offers no agent and resolves any recorded path to a scope that loads nothing, never Everything. Core ships no `.agent` reader, no `Agents/` template and no `.agent` in the set of files whose frontmatter carries access verbs — a distribution registers its kind with `registerAccessFrontmatterExtensions`, as before. A distribution's resolver narrows a connection by returning `ConnectionScope.narrowed(agent, roots, fingerprint)` — skill roots, connector roots and platform tool names (null for all) — read through the person's read gate on every resolve, so an edit reaches the connections made as it at the next catalog revision without a reconnect, and a list can only take away from what the person may read, never add to it; `ConnectionScope.unavailable`/`gone` for a configuration that cannot be used. `tools/list`, `tools_info`, `list_skills`, `get_skill`, `prompts/list`, `list_tool_setup`, `list_local_tools`, the agent guide and the handshake text all follow the narrowed surface; `platformTools` decides which tools the agent is offered, never which prompts it has — the skills its roots name are served as prompts whatever tools it offers (the two skill routes, which both MCP servers read prompts through, and `list_local_tools`, which the local server reads at startup for the connectors it must materialize, are narrowed to the connection's skills and connectors rather than refused); a call to a platform tool outside it is refused at its route (`403`, code `not_available_to_connection`) and the MCP proxy refuses any other off-surface tool with the same sentence, naming the agent. A chosen configuration that is gone, no longer readable or not usable makes the connection load nothing, with one sentence saying why (in `tools/list`'s `_meta`, every call's answer and the handshake), never Everything.

New in the backend: the `modules/agent-scope` module (`ConnectionScope`, `resolveConnectionScope`, `noAgentConfigurations`, the `IAgentScopeResolver` contract), `CorePorts.agentScope`, `GET /api/mcp/agent-choices`, `agentPath` on `POST /api/mcp/external-api-keys` and `POST /api/mcp/oauth/complete`, optional narrowing arguments on `ISkillService` and `IToolManualService` reads, and an optional `connectionScope` on `ToolContext`. Both "Connect as" forms keep Create key and Finish disabled until the agents on offer have answered; the state they hold is one hook of the frontend's agents module, `useConnectAsChoice`. The skills and tool-manuals module entries now export `SkillService`, `PendingSkillsService`, `ToolManualService` and `PendingToolsService` as types only; a host that constructs one imports its file, as the composition root does. `@bevel-software/platform-shared` adds `pathUnderRoot`, the one containment test for KB paths named by a list of roots (`skillUnderRoot` now calls it).
