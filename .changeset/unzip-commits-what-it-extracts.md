An extracted archive lands as one commit, through the agent `unzip` tool and the app's unzip route alike. Every entry is judged before anything is written: the path rules, the size caps, and the archive's rule files (below); a directory entry also meets the write rule on a protected branch and read-before-write for a folder. The files that pass then go through the lock-aware filesystem's batch as the person (`LockingFilesystem.writeFiles`): every path's lock, then one commit. Each file's lock asks the write rule on a protected branch and the read-before-write check, and a file whose lock either refuses is skipped and reported with that refusal. What is on disk at an entry's target (a symbolic link on its way, the git folder it resolves into) is asked only once the entry's gates have let it through: a directory entry's after the judge, a file's under its lock, by the one check `apply_file_upload` asks too; before, the extraction looked first, so a skipped entry's reason told a link in a folder the person cannot read from a plain path. Both doors ask whether the person may change the folder the archive extracts into (read-before-write, as a folder) before that folder is looked at for a link; the agent tool did not ask before, and now refuses a destination inside a folder the person cannot read whole, as the route did. Before, the tool left the extracted files uncommitted until each was saved, and the route wrote them all to disk and then committed them one file at a time. A branch's reads now answer from the access rules of the commit its checkout stands on, so either way a file the archive's own `access.md` restricts could be read by its folder's readers until that `access.md` was committed.

An archive's own `access.md` and `.bevelignore` land in the same commit as its files, when the person may write them. If one of them cannot land, for whatever reason (the write rule, read-before-write, the agent's write hook or its run's write policy, a size cap, an entry that cannot be read), nothing in the archive lands, so files never arrive without the restriction they came with. An archive that would put `roles.yaml`, `groups.yaml` or `synced-groups.yaml` at the repository root is refused whole with a 422, at both doors; before, the tool skipped a `roles.yaml` and extracted the rest, and the route extracted it unchecked. A plugin manifest is extracted like any file.

If any path the archive would write is held for editing, by anyone, nothing is extracted: after the batch's few seconds of retries the call answers 409 naming the path. So does an extraction that loses one of its locks before its commit (it lapsed and was taken since), and nothing it wrote to that path is committed. Before, the tool wrote over that file, and the route wrote every file and then stopped at it, leaving the files after it uncommitted. On a protected branch, an entry the person may not write is skipped with the write rule's refusal; before, the route stopped at it the same way with a 403, and the tool wrote it to disk. A file's lock whose check fails rather than answers refuses the extraction, with nothing written. Directory entries are created once the files have landed, and not at all when the extraction is refused. One that cannot be created then, because a file already sits at its path, is skipped with a fixed reason, and the call answers as usual; before, it answered 500, naming a server path, after the files had been committed. When the commit lands but its push needs resolution, the directory entries are created too, and the call answers with that error: the files are committed, and only their sharing is pending. Files extracted into a new folder directly under a root the person cannot read land with their read grant (the folder's `access.md`) in the same commit; the route used to commit that grant on its own first, and the tool wrote none.

An extraction now lands at most 5,000 entries and 128 MB, the caps `apply_file_upload` already had (before: 10,000 and 500 MB), and at most 100 MB in one file, as before; entries past them are skipped with the reason. Both surfaces now plan an archive with one planner, `planZipEntries`, so they read the same archive the same way. macOS metadata (`__MACOSX/…`, `.DS_Store` and `._` files) counts toward no cap and is never reported; before, an extraction counted it toward its entry cap and listed the metadata past that cap in `skipped`. The 128 MB counts every file the caps let through, one skipped afterwards by the judge or for a link on its path included; before, it counted only the files extracted. An entry that is a symbolic link is skipped ("Entry is a symbolic link, not a file"), and when it is one of the archive's access rules nothing lands; before, the link's target text was written out as a file, an `access.md` included. A directory entry at the path of a file entry of the same archive is skipped with the reason, and the file lands; before, the call failed with a 500. `WorkspaceService.unzipFile(workspaceId, zipPath, destination, judge, landing)` takes how its entries are judged as an `ArchiveEntryJudge` (before, a per-entry guard function) and where the files land as a required fifth argument (`LockingFilesystem` satisfies it); `destination` and `judge` may be `undefined` but are passed. It holds every file's bytes in memory until they land, at most the 128 MB extraction cap besides the archive itself.
