An extracted archive lands as one commit, through the agent `unzip` tool and the app's unzip route alike. Every entry is judged before anything is written: the path rules, the size caps, and, for each file, the write rule on a protected branch and the read-before-write check its lock would ask. An entry one of them refuses is skipped and reported. The files that pass then go through the lock-aware filesystem's batch as the person (`LockingFilesystem.writeFiles`): every path's lock, then one commit. An `access.md` that came in an archive and the files beside it that pass therefore enter the same commit. Before, the tool left the extracted files uncommitted until each was saved, and the route wrote them all to disk and then committed them one file at a time. A branch's reads now answer from the access rules of the commit its checkout stands on, so either way a file the archive's own `access.md` restricts could be read by its folder's readers until that `access.md` was committed.

If any path the archive would write is held for editing, by anyone, nothing is extracted: after the batch's few seconds of retries the call answers 409 naming the path. Before, the tool wrote over that file, and the route wrote every file and then stopped at it, leaving the files after it uncommitted. On a protected branch, an entry the person may not write is skipped with the write rule's refusal; before, the route stopped at it the same way with a 403, and the tool wrote it to disk. Directory entries are created once the files have landed, and not at all when the extraction is refused. Files extracted into a new folder directly under a root the person cannot read land with their read grant (the folder's `access.md`) in the same commit; the route used to commit that grant on its own first, and the tool wrote none. The tool's output schema keeps an optional `unsaved` field, which no extraction reports.

`WorkspaceService.unzipFile(workspaceId, zipPath, destination, guardWrite, landing)` takes where the files land as a required fifth argument (`LockingFilesystem` satisfies it); `destination` and `guardWrite` may be `undefined` but are passed. It holds every file's bytes in memory until they land, at most the 500 MB extraction cap besides the archive itself.
