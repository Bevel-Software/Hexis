A tool's stored keys now go with the tool when its definition leaves the catalog by any route, not only when it is deleted from its tool page. Each scan of the default branch is compared with the previous one. A name's keys are kept only when the name is still declared in a file that declared it before (an edit in place) or from the same bytes as before (a move, or a rename of a file that writes its `id`). Otherwise the values stored under that name are wiped the same way a delete from the tool page wipes them. That covers a deleted `.tool`, a server dropped from `mcp.json`, a changed id, and a deletion followed at once by a different file that reuses the name: written back to back, the two still count as a removal. Once the wipe succeeds, the tool that reuses the name starts with no shared key: the old value is not shown as set and is not sent. A move that also changes the file in the same commit is not recognised as the same tool, so its keys must be set again. Moving a server to another plugin's `mcp.json` behaves the same unless the two files end up byte-identical. A wipe that fails stays owed and is retried on every later scan; until it succeeds, a tool reusing the name can still see the old value. A file with no `id` is named after its file, so renaming it wipes the keys of the old name. A scan that could not see every declaration wipes nothing. That covers a folder, a `.tool` file, an `mcp.json` or the bundle registry it could not read, an `mcp.json` that does not parse as a server map, and a refused `.tool` that names no manual. A refused edit that still names its manual keeps that manual's keys. A removal is noticed only once the running server has completed one scan to compare against. A tool removed while the server was down is not noticed after the restart.
