Every commit the git service lands is announced to the file-change notifier — a single-file save, an autosave checkpoint, a batch (`write_files`, `delete_folder`, an applied upload, the admin roster commits, a plugin rename), a merge, a `commit_change` — from one place: the git service reports each commit it lands through `VersionControlHooks.onCommitLanded`, and the composition root hands that to the notifier once. Before, the single-file save path and the batch construction sites that were handed the notifier announced; a batch built without it — the agent tools' filesystem, the diff routes, the admin roster commits, the synced-groups committer — landed silently (catalogs stayed stale for a TTL, the id index was not repaired, a status set by a batch fired no watcher), and so did an autosave checkpoint, a merge and a `commit_change`.

The announcement is made when the commit lands — pushed, or awaiting its push. A listener that only reads is unaffected by locks. A listener that writes an announced path acquires its lock like any writer: a batch's committer releases its locks once the commit's push has gone through or been handed off to the recovery worker (the push then still owed, the lock no longer guarding the path) — the lock-aware filesystem's acquire retries (three attempts, two seconds apart) cover the usual push, and a push that outlasts them leaves the writer to skip; an autosave checkpoint is announced while the editor's own lock is held, for as long as the person edits, so such a write cannot be made then. A writer that could not lock treats it as "not now", as the id-repair already does, and catches up on the path's next announcement — the editor's release commit when it carries new bytes, the file's next change (before this release neither case was announced at all). Paths are workspace-relative, sorted and unique; the notifier shapes them.

The database pool now listens for an idle connection the server closes (a restart, a forced drop, a terminated backend): the event is logged and the next query opens a fresh connection, where before an unlistened `error` event could end the process.

For implementers: `LockingFilesystemContext.fileChanges` no longer exists, so a constructor that passed it fails to compile — drop the field; the git layer announces. `VersionControlService` no longer takes a `FileChangeNotifier`; the changed optional trailing constructor parameters are `events`, `hooks` and `changeRequestHooks`, followed by the unchanged optional `accounts`. `IVersionControlService` is unchanged. A listener on the notifier that writes (the enterprise id-repair) may now be told of a path whose lock its committer is still releasing — it re-acquires through the lock-aware filesystem's retries, as its rewrite already does — or of an autosave checkpoint whose lock the editor keeps; that write fails to acquire, which it already treats as "not now", and the release commit announces the path again.
