A `SKILL.md` written outside `Plugins/` is refused with the path that would work, instead of committing successfully and producing no skill. A skill is found by where it sits — the catalog scanner, the pending-skill shelf and the plugin pages all read `Plugins/` and nothing else — but `SKILL.md` appeared only in that read-side code, so a write anywhere else passed every gate, committed, pushed and reported success while the product ignored it. There was no warning when such a change request was proposed, none when it merged, and no trace in the Library: the file was real and the skill did not exist. A change request adding `Skills/example/SKILL.md` — correct when it was written, then left behind by the `Skills/` → `Groups/` → `Plugins/` migrations — would still merge cleanly today and change nothing. Both raw write paths now check placement before any byte lands: the agent's file tools through the lock-aware filesystem's `validateWrite` hook (alongside the `roles.yaml` guard it already carried) and the editor's save route. The rule is the catalog's own — under `Plugins/`, in some folder below it — so a skill whose folder IS the plugin (`Plugins/loose-skill/SKILL.md`) still saves, and only a `SKILL.md` no reader could ever find is refused. Moving a file is untouched, so a legacy skill left in the old root can still be relocated into place.
