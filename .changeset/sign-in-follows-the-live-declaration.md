A declared sign-in follows the tool file as it is now. When a person starts a sign-in on a variable whose `oauth` block names a client id, the client id, authorize and token endpoints, PKCE, resource and authorize parameters come from the declaration as the file reads on the default branch at that moment (read afresh, not from the catalog's cached scan), completed from the server's OAuth metadata as the catalog completes them; the owner's stored row contributes the client secret only. A client id changed in the file after the secret was saved is the one used, with no second save. This moves what keeps the secret where it was saved for: it used to be bound to the token endpoint pinned at its save, and it now goes to the token endpoint the file declares at each start, so whoever can write the tool file can move it (to an https, public host only). That trade was decided on the ticket; a start whose declared token endpoint differs from the one recorded at the save logs a warning naming both origins. The endpoints are validated as the client-secret save validates them (https, no private or local address) before anything is written or sent, and a file the parser refuses for such an endpoint (a `.tool`, or a `plugin.json` sign-in) answers the start with the parser's reason rather than "Tool or variable not found"; a declaration whose endpoints cannot be discovered is refused with the discovery's reason, in the save's wording; a variable whose `oauth` block was removed, or a declared client whose owner stored no secret, is refused with "owner hasn't finished setting this up". The caller's row records the configuration the start used, so the exchange and later refreshes of that grant use the endpoints and client id the consent was given for; tokens a person already holds are left alone until the provider refuses them. A sign-in the platform registered itself (`oauth-auto`) starts from its stored row as before, and the client-secret save still stores the provider configuration, now as a record for `adminConfigured` and `list_tool_setup`. `IToolManualService` gains `liveDeclaration`, a `plugin.json` server skipped for a malformed `variables` declaration now says which rule it broke in its log line, locating the entry by position (`variables[0]`) as the `.tool` parser does, never by the name it declared, and `ISecretsVaultService.beginToolOAuthByKey` takes an optional `provider`.

On the tool page, an owner who can write a tool sees "Replace client secret" on a declared sign-in row whenever a secret is stored, signed in or not, and "Set client secret" while none is; a reader, and a platform-registered sign-in, see neither.
