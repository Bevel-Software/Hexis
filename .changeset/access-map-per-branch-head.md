A branch's reads are answered from a map of the commit its checkout stands on. The map holds that commit's access model and the few files that declare access of their own, so the file tree, search and every other batch check open no file to learn that a file declares nothing, and the checkout is no longer walked again every five seconds for its rules. What a file version declares is remembered by its object id. It is read from the checkout, only the start of the file up to its frontmatter's end, wherever `git diff-index <commit>` (git's stat cache, asked before and after the reads) says the checkout holds that commit's version and git can have written it out only as it is: git's configuration names no filter driver (a `smudge` or `process` command; git-lfs installs one, and while one is configured every file is read through git, since a file smudged under an attribute since removed keeps its smudged bytes), no `working-tree-encoding` or `ident` attribute applies to it (one `git check-attr`), and it is the version's size, which an end-of-line conversion never leaves it. A file that differs on disk, that git converts on checkout, or that changed while it was read, is read through git as the commit has it. The map holds the commit's versions only, so an edit counts once it is committed. A head that moves by one saved file costs one `git ls-tree` and two `git diff-index`, and one read of that file: of its start from the checkout, after one `git config --list`, one `git check-attr` and one `stat`, or through git when it is an `access.md` or git converts it on checkout. When the saved file is an access file (`roles.yaml`, a groups file, an `access.md`, a plugin manifest), all the access files are read once more. After a restart the maps begin from one row in the new `access_head_seeds` table (migration `0024`: the last commit a map was made of and the paths and object ids of the files that declare something; no rule and no person), read only by the release that wrote it; without it, or after an upgrade, the start of every file is read once. A first map that needs more than 8 MB of reads is read in the background, and the checkout answers until it is ready; a smaller one is waited for.

The checkout still answers where a map cannot: a path the commit does not hold (written and not yet committed, or untracked), a workspace reported changed, until its head moves or for ten seconds when it does not, a commit that holds a symbolic link or a submodule, a repository with no readable `roles.yaml`, and the single-file gates' read of a file's own entries.

Two things change. A change written to a checkout that nothing reports and that is not committed is seen when it is committed, where the five-second reload used to pick it up. And an `access.md`, `roles.yaml` or groups file that git does not track is no longer a rule for the workspaces a map answers.
