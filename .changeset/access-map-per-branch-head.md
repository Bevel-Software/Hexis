A branch's reads are answered from a map of the commit its checkout stands on. The map holds that commit's access model and the few files that declare access of their own, so the file tree, search and every other batch check open no file to learn that a file declares nothing, and the checkout is no longer walked again every five seconds for its rules. What a file version declares is remembered by its object id. It is read from the checkout where the file there is that version's own bytes: read whole, it hashes to the version's object id. Git's stat cache (`git diff-index <commit>`) only spares that read for a file git already knows differs; it is no proof by itself, since git calls a file the same after its filters, end-of-line conversion and `working-tree-encoding` have run, under whatever attributes and configuration held when the file was written out. A file that differs on disk, or whose bytes are not the version's, is read through git as the commit has it. The map holds the commit's versions only, so an edit counts once it is committed. A head that moves by one saved file costs one `git ls-tree`, one `git diff-index` and, when no map has read that version before, one whole read of it: from the checkout, or through git when it is an `access.md` or its bytes on disk are not the version's. When the saved file is an access file (`roles.yaml`, a groups file, an `access.md`, a plugin manifest), all the access files are read once more. After a restart the maps begin from one row in the new `access_head_seeds` table (migration `0024`: the last commit a map was made of and the paths and object ids of the files that declare something; no rule and no person), read only by the build that wrote it (the row names the build's git sha and how it reads the files; a build that reports no sha neither reads nor writes it); without it, or on the first start of another build, every file version is read once, in full. A first map that needs more than 8 MB of reads is read in the background, and the checkout answers until it is ready; a smaller one is waited for.

The checkout still answers where a map cannot: a path the commit does not hold (written and not yet committed, or untracked), a workspace reported changed, until its head moves or for ten seconds when it does not, a commit that holds a symbolic link or a submodule, and a repository with no readable `roles.yaml`. A single-file gate reads as a batch does: where a map answers, the rules and a committed file's own entries both come from it, and a file the commit does not hold has its own entries read from the checkout; where none does, both come from the checkout, the file's own entries read fresh from disk, as before. A gate's yes on a committed file (read, write, download, owner, and what `explainAccess` reports) also needs the file as it is on disk to allow it under the same rules, so a denial written into the file holds before it is committed; the copy on disk never grants what the commit's copy refuses. A preview of a move reads both the rules and the moved thing from the checkout, which is where the moved thing is read from.

Two things change. A change written to a checkout that nothing reports and that is not committed is seen when it is committed, where the five-second reload used to pick it up. And an `access.md`, `roles.yaml` or groups file that git does not track is no longer a rule for the workspaces a map answers.
