A save the commit worker gave up on (`needs_attention`) no longer blocks merges out of its branch once nothing of it is left to push. Before a merge or an update would be refused over such saves, and once at startup, each is checked against git: when the file is the same in the working copy as in the branch's last commit (both absent counts) and the shared repository's branch holds that version, or when its workspace folder is shown absent and no copy of it was set aside (a folder that cannot be read is not absent), the save is removed, with one log line naming the branch, the path and when it was queued. A save whose change is still missing, or that could not be checked (git failed, the repository was unreachable, its workspace could not be read), is kept and the merge is refused as before; so is one whose check did not finish within the 20-second wait of the merge or update, or whose working copy was set aside while it was checked. So is every save of a workspace whose working copy was set aside when the repository was replaced or moved: that copy may hold its bytes. When failed saves refuse it (`pending-commits` with `needsAttention`, from `merge_branch`, `update_branch` and `mergeBranch`/`updateBranch`), the refusal now carries `stuck`: up to ten of the stuck files the caller may read, and `more`, how many others there are; a file the caller may not read is counted, never named. Saving such a file again lands it, and once that save is committed and pushed, the older failed saves of the file on that branch are removed, set-aside or not, each with one log line.
