A save the commit worker gave up on (`needs_attention`) no longer blocks merges out of its branch once nothing of it is left to push. Before a merge or an update would be refused over such saves, and once at startup, each is checked against git: when the file is the same in the working copy as in the branch's last commit (both absent counts) and the shared repository's branch holds that version, or when its workspace folder is shown absent (a folder that cannot be read is not), the save is removed, with one log line naming the branch, the path and when it was queued. A save whose change is still missing, or that could not be checked (git failed, the repository was unreachable, its workspace could not be read), is kept and the merge is refused as before. When failed saves refuse it (`pending-commits` with `needsAttention`, from `merge_branch`, `update_branch` and `mergeBranch`/`updateBranch`), the refusal now carries `stuck`: up to ten of the stuck files the caller may read, and `more`, how many others there are; a file the caller may not read is counted, never named. Saving such a file again lands it, and its old save then clears the same way.
