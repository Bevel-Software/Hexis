An app can add settings pages of its own. A profile-menu row (`AdminMenuItem`) that declares a `path` and a `page` is mounted inside the settings layout beside the built-in pages, and listed in the settings sidebar under its section, including a section the app defines itself (such as "Infrastructure only"). The row's `isShown` decides who sees it in the sidebar, as it does in the menu. Until now a row could open a dialog, run an action or name a path somewhere else in the app, but it could not bring a page into the settings screen. The path is one absolute address, written as the browser and the router both read it. A row brings no page when its path is a route pattern (a parameter, a splat, an optional segment), has a query or a fragment, is relative, or is a spelling either of them would resolve to something else (`/teams/../secrets`, a doubled slash, a backslash, a percent-encoded letter). A page is mounted only at an address nothing else answers. A row has its page neither mounted nor listed when its path is a built-in settings page (`/secrets`), a route the shell answers itself (`/connect`, `/change-requests/<number>` and the like), an app's path or anything under it, a top-level route of the registry, or a path an earlier row named (with or without a page). Paths are matched as the router matches them, so `/SECRETS`, `/secrets/` and `/%73ecrets` name the `/secrets` page. A row that also opens a dialog or runs an action is not listed in the sidebar; it stays in the profile menu.

`isSettingsNavPath` takes the list of paths to judge against as an optional second argument (`useSettingsNavPaths()` gives the full list, built-in pages and the app's); with one argument it answers for the built-in pages as before.
