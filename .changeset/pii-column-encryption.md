Personal data in the database is now AES-256-GCM ciphertext: emails, display names and avatar addresses, including the copies on approvals, merge log entries, review comments, change requests, queued commits, file locks and plugin join requests; change-request titles and bodies; review comment bodies; and the error text the merge log, the commit queue, a join request and a change request's refused apply keep. The key is derived from `SECRETS_ENC_KEY`, so there is nothing new to set, and a database dump, an injected query or a leaked database credential yields no personal data. The first start after the upgrade seals the rows that are there; nothing to do. From this release, losing `SECRETS_ENC_KEY` loses this data too: keep a copy outside the server.

Equality on an encrypted column goes through a deterministic blind index beside it (`*_bidx`): sign-in, account upserts, approval idempotency, join-request uniqueness and account erasure all key on it, and the unique constraints moved there (`users_email_bidx_unq`, `pr_file_approvals_bidx_unq`, `plugin_join_requests_requester_bidx_plugin_unq`). Erasure rewrites the index to the placeholder's and refuses to run on a row the configured key cannot open.

The key belongs to the database handle, not to the process: `createDb`/`getDb` take a `piiKey`, and `createCoreServices` builds its handle with the knowledge base's `SECRETS_ENC_KEY`. A process that serves several knowledge bases therefore seals each tenant's rows under that tenant's own derived key, the one that already seals its stored credentials, so a tenant's dump opens whole with its one key and no tenant's key opens another's rows (docs/multi-tenant.md).

**Anything that reads or writes these tables with its own SQL breaks, and must be adapted before it takes this version.** A statement that filters on `users.email` (or any sealed column) matches nothing; an insert into `users` without `email_bidx` fails, and `ON CONFLICT (email)` has no constraint left to name. With drizzle on a handle that holds the key, write and compare the index column with the address itself (`emailBidx: email`, `eq(users.emailBidx, email)`) and the handle stores or binds its index; reads come back as plaintext. With SQL written by hand, `derivePiiKeys(secretsEncKey)` (or `piiKeysOf(db)`) gives `index(email)` to compare `email_bidx` with and `seal(value)` for each sealed column; for a tenant the key is `deriveTenantSecrets(masterKey, slug).secretsEncKey`, so the same address has a different index in every tenant. A handle built without a key refuses to write personal data. Stop the old version before starting this one, and take a database backup first: an older version reads the sealed columns as ciphertext, so there is no downgrade without it (UPGRADING.md).

For overlays: `encryptedText` and `blindIndexText` are the column types for an overlay's own personal-data columns; they hold no key and work on the handle the composition root built. `derivePiiKeys`, `piiKeysOf`, `isEncryptedBlob` and `PII_CIPHERTEXT_PREFIX` are exported for code that handles the stored form itself. `runCoreMigrations` now also seals the core rows under its lock, and refuses a handle that holds no key. Never `eq()` an encrypted column: the ciphertext is randomized, so compare the blind index. A value interpolated into a raw `sql` template is not bound through its column, so an index compared that way must be `index(…)`ed by hand.
