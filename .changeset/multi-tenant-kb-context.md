One process can now serve several knowledge bases, one per host name (`docs/multi-tenant.md`). Set `TENANTS_FILE` and `TENANT_MASTER_KEY` and each tenant gets its own repository, admin, users, settings, secrets and Postgres schema, built on its first request by the same code a single-tenant deployment runs and stopped again when idle. A deployment that serves one knowledge base changes nothing: it keeps `public`, its lock ids and its migration ledger, and its setup screen works as before, with a saved git token in effect at once and no longer published to the process environment. `DB_SCHEMA` lets a single-tenant deployment keep its tables on a schema of its own, which is what a tenant moved to a dedicated deployment arrives with. The schema travels as a connection startup parameter, so only session-mode pooling is supported in front of a process that serves several knowledge bases; a tenant refuses to start on a connection that lost it.

For overlay and integration authors:

- The server no longer reads the branch model, folder layout or checkout folder name from the shared package's live bindings; they travel as one `KbContext` the composition root builds and hands to every service in the slot where `kbDirName` went. The shared helpers take the layout or model they answer for (`isPlatformFile(path, layout)`, `reservedRootDirNames(layout)`, `isProtectedBranch(model, name)`, `agentsFilePointerSentence(agentsFile)`, …): pass `core.kb.layout` / `core.kb.branchModel` on the server and `currentKbLayout()` / `currentBranchModel()` in the browser. A lint rule keeps the server packages off the bindings; `CorePorts.mirrorSharedBindings` (on by default) keeps them filled for an overlay that still reads them.
- Git credentials are a provider on the runner (`IGitRunner.credentials`, `gitCredentials()`); nothing writes `GITHUB_TOKEN` into `process.env` any more, `DeploymentSettingsService.syncGitTokenEnv` is gone, `redactGitToken(text, token)` takes the token, and `WorkspaceService` and `KbStartupRunner` no longer take a git username of their own.
- `createCoreServices` takes a `TenantConfig` (`CoreConfig` implements it and `ProcessConfig`); `DeploymentSettingsService` resolves its env-first layer against `TenantConfig.settingsEnv` when one is given, so a tenant's record values behave as environment-pinned ones and the host process's variables never reach a tenant; `createDb(url, { schema })`, `closeDb`, `startCore`, `stopCore` and the `tenancy` module (`TenantSource`, `StaticTenantSource`, `createTenantHost`, `deriveTenantSecrets`) are exported. `runCoreMigrations` and `runEnterpriseMigrations` place the ledger in the handle's schema.
- `CorePorts.accountAdmission` is asked before any account is created (a first SSO sign-in, an admin creating one, the owner's bootstrap sign-in, an embed identity); a refusal answers 403 with the port's words and the login screen names it. Core admits everyone.
