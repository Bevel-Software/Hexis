The Knowledge explorer and the Skills & Tools tree take their roots from the repository checkout, by name, and never from a search of the workspace for a folder that looks like a knowledge base.

Both sidebars used to find the repository by walking down from the workspace root until they met a level whose children included a well-known folder name — `KnowledgeBase`, `Plugins`, `Skills` and the rest — and then splitting that level into their sections. That works only while nothing outside the repository carries one of those names. On core-staging something did: a stray `KnowledgeBase/` and `Plugins/` had been written beside the checkout, the walk stopped at the workspace root, and every sidebar read the wrong directory. The stray `KnowledgeBase/` became "Knowledge", the real checkout was folded in underneath it as an ordinary content folder, eight test documents appeared below the divider, the Skills tree found no `Skills/` and showed Empty, and the Plugins tree listed the one stray plugin instead of the ten real ones. Nothing in the repository was wrong.

The root is now a lookup, not a guess. The deployment names the checkout folder and the bootstrap response already carries that name, so the Knowledge explorer resolves `<kbDirName>/` as the direct child of the workspace tree and splits THAT folder's children into Knowledge, Data, Agents and Pipelines; the Skills & Tools tree resolves `Skills/` and `Plugins/` as children of the same folder. Nothing above the checkout is read by anything: the folded-in content folders, the loose files under the divider, the pinned rows and the pages offered on the empty viewer all come from inside `<kbDirName>/`, so a `KnowledgeBase/`, a `Plugins/`, a `Skills/` and any number of loose files beside the checkout leave both trees rendering exactly what they render without them.

When the checkout is not in the workspace tree at all, both trees now say so — "Nothing to show here: the repository checkout is missing" — and render no section, folder or file from anywhere else. There is no fall back to whatever directory happens to be there, because that fallback is the code path this bug came out of, kept alive for exactly the case in which it is most likely to misfire. A checkout that is present but empty keeps its own, different answer ("This knowledge base is empty"), and a reader the access filter left with nothing still hears that nothing is shared with them rather than a diagnosis of the deployment.

A knowledge base that predates the `KnowledgeBase/` split has no named roots to section by, so its checkout folder is drawn as the tree — and drawn as the ROOT of it, which it now is: no drag, no rename, no Copy path, and the root's Add files and Add folder pickers on it. Before, that layout rooted the tree at the workspace directory above the clone and offered the clone itself as an ordinary draggable folder.

Nothing about paths changed: deep links, file operations, drag and drop, uploads and the URL-to-path mapping all address the same paths under `<kbDirName>/` they addressed before. Writes made from the root row are addressed by the checkout's own path rather than as a bare workspace root, which is the same folder the server already resolved them to.
