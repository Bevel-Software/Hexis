Upgrade notes for the batch-write and archive changes in this release, for code that imports from `@bevel-software/platform-core-backend/modules/*` or calls the routes and tools named here.

- `PathHeldError` is a new export of `modules/kb-fs`. The lock-aware filesystem (`LockingFilesystem`) throws it when another holder keeps a path's lock past the retries; nothing of that write was written. It carries `path`, `holderName` and `lapsed` (true when the batch lost a lock it held, below), and its message names the path and its holder and says nothing was written ("Skipped editing … — locked by …. Nothing of this write was written; try again later."), or, when `lapsed`, that the write could not confirm it still held its lock and nothing was committed (a held lock's message used to end "Continuing with other edits; try this one again later.", which was wrong for a batch that wrote nothing). It is a `VersionControlDomainError` with status 409 and the payload `{ kind: 'path-held', path }`, so a route or tool that passes it on answers a held lock as a 409 with that body, where it used to answer a 500: the agent tools that write through that filesystem (`write_file`, `write_files`, `edit_file`, `delete_folder` and `apply_file_upload` among them) now do. `POST /workspace/:id/unzip` and the `unzip` tool answer a held lock with the same 409 and payload, in their own sentence ("… so nothing was extracted. Try again once they are done."). Code that tests `instanceof VersionControlDomainError` before it tests for a held lock now meets this one there; test `PathHeldError` first to answer it in your own words, as the starter-pack route now does.
- `ArchiveRefusedError` is a new export of `modules/workspace/workspace.service.js`: an archive refused whole, with nothing written and no lock left held. `POST /workspace/:id/unzip`, the `unzip` tool and `apply_file_upload` answer it with a new error body, `{ kind: 'archive-refused', entry, error }`, where `entry` is the workspace path (or, when it has none, the name in the archive) of the entry that decided it. Its status is 422 for a `roles.yaml` or groups file at the repository root, and, for one of the archive's own access rules that cannot land, the status of the refusal that stopped it when that is a 4xx, and 422 otherwise (a refusal with no status, or a 5xx such as a failing write hook's).
- `archiveEntryJudge` is a new export of `modules/workspace/workspace.tools.js`: the one `ArchiveEntryJudge` that both unzip doors and `apply_file_upload` use.
- `planZipEntries(zip, destination, limits)` is a new export of `modules/workspace/zip-entry-rules.js`, with its types `ZipPlanLimits`, `PlannableZipEntry`, `ZipPlanStep`, `ZipPlanSkip` and `ZipSkipReason`: the one plan of an archive that `WorkspaceService.unzipFile` and `apply_file_upload` both land. It reads the archive and returns one step per entry, in the archive's order: a file with its workspace path and bytes, a directory entry, or a skipped entry with a reason code. It never touches the filesystem. `ONE_COMMIT_LIMITS` is a new export of `modules/workspace/workspace.service.js`: the limits both hand it (5,000 entries, 128 MB in all, 100 MB in one file).
- `WorkspaceService.unzipFile` no longer asks, itself, whether an entry would create the checkout folder's own name at the repository root: `archiveEntryJudge`'s `entry` refuses such an entry, and an extraction with no judge hands it to the landing. Pass `archiveEntryJudge`, as both unzip doors do.
- `LockingFilesystem.writeFiles` takes a fifth, optional parameter, `refused(path, err)`, asked when taking a write's lock throws (the lock's own gates refusing that path, or the lock service failing): returning drops that write and the batch goes on, throwing refuses the whole batch with nothing written. Without it, such a throw refuses the batch, as before. The method is now generic over its content type (`writeFiles<C extends FileContent>`), so `check` is handed, and returns, writes of the caller's own content type.
- Every `writeFiles` batch now keeps the locks it holds as its own, whoever calls it, downstream callers included. It keeps the `acquiredAt` of every lock it is granted, and a lock stays its own only while a heartbeat (`heartbeatLock`) succeeds and answers that same `acquiredAt`. It renews its locks every third of the lease it was granted (every 20 seconds with the lock service's 60-second lease) until the last of them is given back, its release loop included, and a released path is renewed no more. It also sends one heartbeat for every lock it holds right before its first write and right before its commit, so every batch adds at least two heartbeats per path, sixteen at a time; the platform's `heartbeatLock` logs one info line per heartbeat. A heartbeat that throws, or answers another `acquiredAt` (the lease lapsed and the path was taken since, by the same person's editor or second session too), marks that lock lost. A lock lost by either check refuses the batch with `PathHeldError` (409, `{ kind: 'path-held', path }`) naming that path, with `holderName` null, `lapsed` true and a message saying the write could not confirm it still held its lock, and nothing is committed. The batch never releases or discards a lock it knows it lost: both are keyed on the user and would drop the lock and reset the file its new holder now has. Refused right before its commit, it releases the paths still its own as a failed commit does, and what it wrote to a lost path stays on disk under that path's new holder. Nothing looks for a lock lost after the last check, during the commit and its push.
- `platformFileUploadRefusal` in `@bevel-software/platform-shared` is deprecated: nothing refuses with it any more. It stays exported.
