Anyone signed in can invite people. A new signed-in route, `POST /api/invitations` with `{ email, role?, startingPassword? }`, creates a NEW account only: an address that already has one answers `{ status: 'existing' }` and nothing is written to it (no password, no role), whoever asks. `role: 'admin'` is refused with 403 unless the caller is an admin. The starting password is generated on the server (16 letters and digits without 0, O, 1, l and I, from `crypto.randomInt`), stored only as its hash and never logged: for every new account where password sign-in is on and no single sign-on is offered, on request where both are on, and never where password sign-in is off (a request for one is refused with 400). The owner's address and the system accounts' addresses never get one, whatever the deployment; an address that grants or groups already name gets one like any other. The account-invited event carries the generated password as `startingPassword` beside `passwordSet`, and a listener may now answer `{ channel, deliveredStartingPassword: true }` to say what it sent the person (their email, the companion) carried it: the route then leaves the password out of its answer and names the channels in `passwordDeliveredBy`. Otherwise the password is returned once in the answer for the inviter to pass on. A plain channel answer claims no delivery, as before. `IAccountHooks.deliverAccountInvited` runs the listeners and reports both. From a non-admin, the password of an address that already holds Admin is never returned: it goes to a listener that can deliver it, and is otherwise discarded, leaving the account with no password (should the discard itself fail, the hash stays but the password is withheld all the same, so nobody holds it; the failure is logged); when Admin membership cannot be read, the address is treated as holding Admin. That lookup runs only after a new account was made, so an address that already has one always answers `existing`, and an existing address costs no password hash. The admission port is asked with the new reason `invite`; a refusal answers 403 with `kind: 'admission'`. Each created account writes one `account audit:` line with `action: 'invite'`, whether a password was generated, the channels that delivered it and whether it was returned, never the password. Each inviter may send 200 invitations per 15 minutes; past that the route answers 429 before any role, account or password work. A listener's failure on an event carrying a password is logged by its shape only (error names, codes and stack frames, never its message or fields). A channel name a listener answers that carries the password as written (whole, or a head of it of 8 characters or more) is not a channel: it counts as not having reached the person, claims no delivery, and is logged without its text, so it reaches neither the answer nor the audit line. Like `/api/admin/accounts`, the route stays open while a deployment is read-only, and the admission port still decides about seats. `POST /api/admin/accounts` is unchanged and stays admin-only.
