`apply_file_upload` lands a zip's own `access.md` and `.bevelignore` in the same commit as its files, when the caller may write them, and judges every path with the archive judge `unzip` uses. Before, it refused those files with `platform_file` and landed the rest, so a download of a restricted folder applied back arrived without its restriction. If one of them cannot land, for whatever reason (the write rule, read-before-write, the write hook or the run's write policy, `mode`, a size cap, an entry that cannot be read), nothing in the upload lands and the call answers with that reason; the token is not spent. A single uploaded file named `access.md` or `.bevelignore` now lands too, by the same rules; before, it was refused with `platform_file`, which nothing answers any more. An upload that would put `roles.yaml`, `groups.yaml` or `synced-groups.yaml` at the repository root is refused whole with a 422; before, a root `roles.yaml` was refused as that one path, and a groups file landed like any file. A plugin manifest lands like any file, as before. Read-before-write is now asked of each path at its lock: a path in a folder the caller cannot read is refused with `write-denied` and the others land, where before the whole apply was refused. `mode` is judged only under the lock, after its gates, so such a path answers `write-denied` even when a file is there, never `exists`. An apply whose commit lands but whose push needs resolution spends its token and answers that error (409, `push-needs-resolution`); before, the token survived it, and a retry answered as if nothing had landed.
