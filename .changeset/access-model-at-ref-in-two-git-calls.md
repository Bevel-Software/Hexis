Change-request listings on a knowledge base with many open requests no longer take minutes. The access model at a commit, which the "for me" listing builds for every open request's two refs, used to read its files one `git show` at a time: a few dozen access files times a hundred refs was thousands of git processes per listing, each forking the server, with the file tree and every other request waiting behind them. A build is now two git commands: one `ls-tree` lists the tree, and a single `cat-file --batch` invocation reads every file the model needs. The cache of built models holds 512 commits instead of 64, enough for a listing's refs so each is built once, and a commit with no roles.yaml is remembered rather than read again on every call. Paths that git would quote (a non-ASCII character in a folder name) are listed as they are, so their access files are read too. A directory where roles.yaml or a groups source was expected is never read as "absent": a roles.yaml that is a directory is malformed configuration, so the ref answers no access (as a roles.yaml that does not parse does) and the gate does not fall through to another ref; a groups source that is a directory makes the model unreadable at that commit, so the gate refuses to decide until the tree is fixed. (A directory named access.md or plugin.json is not an access file in any model, at a ref or in the working tree, and is passed over as before.)
