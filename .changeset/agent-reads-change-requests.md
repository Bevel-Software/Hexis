An agent reads change requests the way the GitHub pull request API offers them — in Hexis's own words.

Five read tools, named and shaped after their GitHub counterparts: `list_change_requests` (filtered by `state`, `head`, `base` and `author`), `get_change_request`, `list_change_request_files`, `list_change_request_reviews` and `list_change_request_comments`. One tool per GitHub endpoint, the same filters, the same paging — and the filters keep GitHub's spelling (`state`, `head`, `base`, `author`, `per_page`, `page`), so an agent that knows GitHub's list can use these without reading the schema.

The ANSWERS speak Hexis. An agent opens a change request with `open_change_request` and reads it back with these five, and answering the first in Hexis's names and the second in GitHub's would make one request two vocabularies. So every field shared with `open_change_request`'s summary takes that summary's name — `url` first, then `number`, `title`, `state`, `sourceBranch`, `targetBranch`, `approvals`, `mergeBlockedReasons`, `files[].path`, `files[].change` — and the rest follow its style. Four differences from GitHub are worth naming: `state` is Hexis's own (`open`, `merged`, `closed`), so a merged request says `merged` instead of `closed` with a flag beside it; every path in every answer is `path`, where GitHub calls a pull-request file's path `filename` and a comment's `path`; a file's kind of change is `added` / `changed` / `deleted` / `moved` from the same function `open_change_request` uses, not git's seven-way status; and an approval a later push invalidated is `stale`, Hexis's word, not GitHub's `DISMISSED`. A reply names the comment it answers `parentId` — the argument `post_change_request_comment` takes to post one.

An APPLIED request is read from the merge commit its row records. Merging retires the source branch, so the branch pair every other diff is built from no longer resolves — and since an empty file set proves no read access, an applied request was readable by its author alone, which is the opposite of catching up on what happened. The merge commit holds exactly what landed, is local, and cannot move: its files are recovered from it (two-dot, against its first parent, so nothing the target did on its own while the request waited is re-reported) and filtered by access like an open request's. Its two parents are the base and head the request spanned, so an approval given before the merge still reads as current rather than stale. The commit is verified to be that request's own — in the clone, two parents, and a subject naming the request — because `merged_sha` was not reliably one: a merge with nothing to merge recorded the TARGET TIP, which in a deployment that lands everything through change requests is usually another request's merge commit, and reading it would have answered with that other request's files under this number. Such a merge now records no sha at all, and a row that already holds one fails closed instead of publishing somebody else's change. One case does still have a commit of its own to record: a merge whose push succeeded and whose row update then failed leaves the request's merge commit on the target, so a retry — which finds nothing left to merge — looks for that commit by the number in its subject and records it, rather than reporting the request as having merged nothing and leaving it fileless for good. The retry has to be let that far, though, and it was not: with its change already on the target the request differs from it by nothing, so its file list is empty and the approval gate refused the attempt — "no file changes to approve" — before any merge ran, leaving the request open, fileless and un-appliable for good. The gate asks the same ownership question itself now, of the target branch alone, and a request that owns a merge commit there is recorded as merged at it instead of being refused. Nothing is merged, committed or pushed by that recovery: the merge already happened, and what was missing was only the row. A target branch that cannot be refreshed answers no commit at all, because the answer is used to record what a request published and a tracking ref the clone could not refresh is no authority for that. The number is kept on the subject git reports: a title is flattened to one line where the subject is built, because `git` takes only the first paragraph of a commit message as its subject and a title may contain a blank line. A DECLINED request is read from nothing, and stays readable by its author alone. Not only because its branch is retired — declining retires the source branch as merging does — but because nothing durable says what it proposed: no sha is recorded, and the branch it came from keeps moving, so reading the branch pair would answer with what that branch differs by NOW. Its author may have committed more to it since, or opened a fresh request from it; the turned-down proposal is not what would come back. An empty file set proves no read access, so it is the author's alone.

Listing closed or merged requests no longer reaches the network. A closed row's source branch is retired, so asking for the branch pair fetched two refs — one of which no longer exists — once per request, and logged a warning for each: a few hundred applied requests opened a few hundred concurrent fetches to answer nothing. A merged row is now diffed from its merge commit, a declined one is not diffed at all, and the clone refresh a list makes is kept only for a set that contains open requests.

Every tool answers only what the caller may read, resolved against the target branch's access tree exactly as the app's own file reads are. A request whose files the caller may read only in part lists the readable ones and says how many are withheld without naming them; the same goes for comments, reviews and merge blockers. A moved file is judged on both of its names, since the diff of a move shows what was at the old one — and the list of requests judges that over the same paired file list the detail of one does, so the two can never disagree about whether a request is visible or how many of its files are withheld. A reply is shown only when the comment it replies to is, up the whole chain: a reply carries no path of its own, so judged on itself it looked like a general comment and came back naming a parent the caller could not see. A request the caller may not see at all answers as not found, word for word what a number that was never issued answers. No tool returns a patch unless asked for one, every list is paged (30 by default, 100 at most), and none of them changes anything.

`body` is what the author wrote. Hexis appends a generated `## Affected owners` block to a change-request body, one line per changed path; the tools cut that block and nothing else, so an author who writes their description in sections keeps it, and a reader of one folder is never handed the name of a file in another. Who must approve each file is read from `list_change_request_files`, where it is access-filtered per file.
