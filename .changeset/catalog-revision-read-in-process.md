The hosted MCP endpoint reads a caller's catalog revision in process. It asks for the revision on every request, to pick the caller's cached tool client, and it asked with an HTTP request to `GET /api/agent/catalog-revision` on the same server, behind a 15 second limit of its own. A busy server answered itself late, the limit fired, and the request built a surface it could not cache. The route and the endpoint now call one reader (`createCatalogRevisionReader` in `core/catalog-revision.ts`), so the two cannot answer differently. The route is unchanged for the local server, which still polls it. The endpoint hands over the request's bearer, and it is resolved as the route's auth resolves it (with the verifier `manualAuth` runs, `createManualTokenVerifier` in `modules/tool-auth`) when the revision is read, so a key revoked after its request was admitted is refused, as the route refused it. When the reader fails or refuses, the request builds a surface of its own and keeps it to itself, as it did when the loopback failed.

The in-process read keeps a 15 second limit, counted differently. The loopback's limit ran on the clock, so a server held busy passed it on a read that needed milliseconds. The new one (`withinLoopTime` in `shared/loop-time-limit.ts`) is spent only while the event loop turns. It is spent in ticks of 250 ms, and a stretch the loop is held for spends one tick, however long the stretch. So a loop held for twenty seconds no longer ends a read that needed milliseconds. It is not a promise about every kind of load: when the loop keeps turning under steady work, the ticks fire on time and the limit runs on the clock, and the read gets every turn of the loop the limit gets. A read that waits on something that never answers still ends. When it ends, the request builds a surface of its own and keeps it to itself, as it did when the loopback request passed its limit.

A surface built while the manual list could not be read is no longer kept. Before this change the list and the revision were both requests the server sent itself, so on a busy server they usually failed together, and a failed revision already kept the surface out of the cache. With the revision read in process, the revision is read while the list request can still fail, and that surface, which holds the platform tools and none of the organisation's, would have been served under a valid revision until the catalog next changed. It is now used for the one request and built again on the next.

`createCatalogRevisionRoutes` takes either a reader (`read`) or the sources to make one from, not both.

A minor release, not a patch: the exported `CoreServices` gains a required member, `readCatalogRevision`. Code that builds or mocks a `CoreServices` by hand must add it.
