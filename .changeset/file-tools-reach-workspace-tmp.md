The file tools read a workspace's `tmp/` folder (where the chat, the SharePoint reader and tool chains stage files) through a reserved ref, `__tmp__/<path>`, resolved against the workspace of the branch the call names. `read_file`, `file_stat`, `grep` (as `path`) and `copy_file` (as `src`) take it, and the file reads through the same readers a repository file gets: a spreadsheet as extracted text with its sheet markers, a PDF, a deck, a Word document and an email as theirs, an image as the picture, text as text. The ref names one file. A folder, the bare prefix, a `..` segment, an absolute path, a backslash, a control character and a link out of the folder are refused with a message naming the rule (`kind: tmp-ref-invalid`), and a missing file is the ordinary not-found naming the ref. The folder is read-only through the ref: every other tool, and any other input (`copy_file`'s `dest` included), refuses one with `kind: tmp-ref-read-only` and says `copy_file` to a repository path is how a file is kept. A copy out of tmp lands through the ordinary repository write (access, lock, reserved names, commit) and never replaces what is there. `WorkspaceService.readFileBinary` accepts the ref under the same rules, so a distribution's own tool can read staged bytes, and `WorkspaceService.statTmpFile` stats one. Every workspace's `tmp/` folder is swept hourly of files last modified more than seven days ago, and of the folders that leaves empty (`WorkspaceService.sweepTmp`, run by `TmpSweeper`, which `startCore` starts and `stopCore` stops). The agent guide's "Working with files" section describes the ref. Its cap rises to 7,400 characters, and the handshake instructions' cap rises to 14,400.
