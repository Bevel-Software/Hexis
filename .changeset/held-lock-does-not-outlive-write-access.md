A held editor lock no longer outlives the write access it was taken under. A save from someone who holds a file's lock is checked against the access rules as they are at the moment of the save, not as they were when Edit took the lock. So when an admin removes their write while they are editing, the save is refused with the same 403 a non-writer gets and nothing is written. On the file routes (`PUT`, `DELETE` and move on `/file`, uploads, folders, and each file of an extracted archive, asked before its bytes land) the refused save also releases the lock, and bytes saved before the grant was removed are still committed. The embed (Edit, Save and its heartbeat) refuses through its own write check and lets go of the lock the same way, through `holdsEditLock` once the write gate refuses, so bytes saved before the grant was removed are committed there too; before, its heartbeat discarded them. An access-rule edit is refused by that route's own write check before the lock is asked about, as before; the lock then ends when the editor lets go of it or it expires. The question goes through one new version-control call, `holdsEditLock`. A caller's own coordination hold no longer counts as holding the lock on the file routes and the access-rule edits: such a save now meets the acquire and is refused as contended (409), as the embed already did. An extracted archive skips an entry that another user locks, or that the caller holds only a coordination hold on, before its bytes land, instead of writing it and then refusing it.
