A held editor lock no longer outlives the write access it was taken under. A save from someone who holds a file's lock is checked against the access rules as they are at the moment of the save, not as they were when Edit took the lock. So when an admin removes their write while they are editing, the save is refused with the same 403 a non-writer gets and nothing is written. On the file routes (`PUT`, `DELETE` and move on `/file`, uploads, folders, and each file of an extracted archive, asked before its bytes land) the refused save also releases the lock, and bytes saved before the grant was removed are still committed. The embed (Edit, Save and its heartbeat) answers its own generic 403 whether its own write check or the version-control gate refuses, never the gate's list of eligible writers, and on its own check's refusal lets go of the viewer's edit lock with the same committing release, so bytes saved before the grant was removed are committed there too; before, its heartbeat discarded them. An access-rule edit is refused by that route's own write check before the lock is asked about, as before; the lock then ends when the editor lets go of it or it expires. The question goes through one new version-control call, `holdsEditLock`. A caller's own coordination hold no longer counts as holding the lock on the file routes and the access-rule edits: such a save now meets the acquire and is refused as contended (409), as the embed already did. An extracted archive now takes each entry's lock before its bytes land, through the same mechanism as the agent's unzip, so an entry the caller may not write, that another user locks, or that the caller holds only a coordination hold on is skipped and reported instead of written and then refused. As in the agent's unzip, a lock is checked to be still the extraction's own before its release, so a long archive whose lock lapsed to someone else (the same person's editor included) leaves that lock alone and answers 409, and the files written before an extraction fails part-way are still committed. An access-rule edit that meets a contended lock now answers that 409 instead of a generic 500.
