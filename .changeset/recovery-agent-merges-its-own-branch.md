The recovery agent can bring the shared branch into the workspace it was spawned for. A queued commit whose push keeps failing is handed to the recovery agent, and the agent's way to rescue it is `update_branch` — but the merge waits for every commit still queued on the branch, and the commit under rescue was one of them, so the agent always heard `pending-commits` and a person had to reconcile the branch by hand. That commit is now `recovering` for as long as the agent runs: no worker pass claims it, and the wait `update_branch` and `merge_branch` make does not count it, so the agent's merge goes through and publishes the branch. Every other queued commit on the branch, a save made during the recovery run included, still holds the merge, and a commit that needs a person still refuses it at once. When the agent returns — finished, gave up or threw — the commit goes back to `pending` and the next pass retries it; one whose change the merge already published lands as a success and leaves the queue. A restart during a recovery run returns it to `pending` at boot. Migration `0019_pending_commits_recovering` widens the `pending_commits.status` check; a core older than this one would leave a `recovering` row unclaimed, so roll back only with no recovery run in flight.
