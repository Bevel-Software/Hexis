Moving a deployment to another repository is now one question, and takes effect on the save. Every move is treated alike: another address, another repository on GitHub, or another way of having a repository. The save is refused until the admin confirms, at the Save button, that every working copy on this server stops being used and is cloned fresh. Anything committed there and never pushed goes out of the app with it, recoverable only from the `replaced-working-copies` folder on the server. When change requests are open, the admin chooses whether to keep them (the repository only moved) or close them as "repository replaced", which also releases the file locks held on their branches. Nothing is deleted either way, and a close that cannot be done refuses the whole save. The confirmed save runs the knowledge-base startup phase with the commit worker stopped, so the app opens on the new repository's content without a restart, and commits still queued for a working copy that was set aside are marked as needing attention instead of being written to the new repository. This replaces the checkbox and the pending restart that a move between ways needed before. An address that differs only in spelling is the same repository and changes nothing.

A boot no longer stops on what the host answered about the repository or the credentials — "repository not found", a rejected token, a refused write — wherever in the phase it was raised: the deployment comes up gated, the setup screen shows the cause in plain words, and saving retries. Every other failure still stops the boot. A refused save now shows the reason the host gave, not only that it did not save.
