The server now stops cleanly, and only one process at a time drains the commit queue.

Stopping: on `SIGTERM` (what Docker sends on every stop and redeploy) or `SIGINT`, the process stops accepting requests, drops its open connections, lets the commit worker finish the commit it is in the middle of, releases its lease, and ends its database pool, in that order and within eight seconds — inside Docker's ten-second grace period, after which the container is killed regardless. A step that does not finish in the time left is abandoned and the next runs: a commit that outlives the deadline is left `running` in the queue, and the lease it was holding is released by the database once the process is gone, so the replacement takes the lease and the queue's recovery returns that row to `pending`. Previously the process simply died: an in-flight push killed mid-write, live-update streams cut without a word, connections left for the database to time out. Live-update streams need nothing new for this: the browser reconnects on its own, and the replacement process answers the reconnect with a full resync, which is what the event bus already does for a client whose history it does not have. An unhandled promise rejection or uncaught exception runs the same sequence before exiting with a failure code, instead of dying on the spot as Node does by default.

Draining: the commit worker runs only while its process holds a Postgres advisory lock, the commit-worker lease. This closes a real gap on every redeploy. Reverse-proxy deployments start the replacement container while the outgoing one is still running, and for that window two processes share one workspaces volume. The queue already stops two workers claiming the same row, but nothing stopped two workers running git in the same clone directory, since the mutex that serializes that lives inside each process. Now the replacement serves requests immediately, declines to drain until the outgoing process exits and its lease is released, and takes over within a few seconds of that. If a holder's database connection drops, it stops draining at once and asks for the lease again rather than carrying on as though it still held it.

The shell that runs the server registers the signal handlers; `createShutdown` is exported for a distribution's own shell to do the same. No configuration is added.
