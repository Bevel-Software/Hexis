A tool manual or skill added, changed or removed on the default branch reaches the connection you already have, without a reconnect. A skill is in the very next `list_skills` or `get_skill`, on either connection — skills are read from the workspace on every request. For tools, the local server checks the catalog when that connection is used, and the change lands at the next check — in the listing that runs it, or after the tool call that triggered it, so a new tool is callable from the call after that one. A commit touching a `.tool`, an `mcp.json`, a `plugin.json` or a `SKILL.md` already dropped the released catalogs whichever path made it — the app, the file tools, or a git push — and the hosted endpoint, being stateless, already rebuilt its tool surface from the live registry on every request; both are now pinned by tests, including that a manual added between two requests is in the second one's answer.

What was missing was the connection nobody can push to. The local `hexis-mcp` server registered the deployment's manuals once, at startup, so a tool committed afterwards stayed invisible there until someone restarted the process. It now checks a new `GET /api/agent/catalog-revision` — a per-caller fingerprint of the tool manuals and skills the caller may read, ACL-filtered by the same services the listings use — whenever the connection is used: when a tool call finishes, and when a client lists the tools. Never on a timer, so an idle connection asks the deployment nothing, and at most once every five seconds however busy the connection is, so a chain of calls costs one read — which also means a listing inside those five seconds answers with the toolset the last check confirmed. On a change it re-registers everything it holds — the deployment's manual and every local-only server (`local: true`, or a `type: "stdio"` command), which is fetched to disk again and whose child process is restarted by the re-registration — and sends the MCP tool-list-changed and prompt-list-changed notifications. A listing waits for that refresh, so the list it returns is the current one. It declares both `listChanged` capabilities so a client knows it may trust the list between them. `/api/config` advertises the route as a `catalogRevision` capability, the same mechanism agent instructions use and for the same reason: an unknown `/api/*` path on an older deployment falls through to the JWT mounts and answers 401, so a probe would tell the user to mint a new connection key over a route that is merely not there. An older deployment says so once on stderr and the server keeps its startup toolset, exactly as before. The one thing that can delay a refresh: it waits for a tool call that is still running before it re-registers, so a commit made mid-call lands once that call finishes.

`list_skills` and `get_skill` no longer disagree about the same skill. The listing resolved read access through the batch gate, which memoizes a file's own frontmatter rules per workspace, while loading by name resolved it through the single-file gate, which reads disk on every call — so a freshly written `SKILL.md` could be loadable by name and absent from the listing, and an author who wrote a skill and then listed them did not see their own work. Both now resolve through the one gate — and that gate is dropped on the same default-branch signal that drops the catalogs, so the listing and the load are refreshed by one event or by neither: a `SKILL.md` that rewrites its own `read:` rules cannot be answered through the previous verdict while the new listing is already live.

`AGENTS.md` states the five-second timeframe and the caveat it depends on: a client that caches the list it was given at connect time, rather than honouring the notification, must re-list or reconnect.
