A tool manual or skill added, changed or removed on the default branch is live within five seconds on the connection you already have, without a reconnect, whenever that connection is in use. A skill is in the very next `list_skills` or `get_skill` on either connection, because skills are read from the workspace on every request. A commit touching a `.tool`, an `mcp.json`, a `plugin.json` or a `SKILL.md` drops the released catalogs whichever path made it, and the hosted endpoint, being stateless, already rebuilt its tool surface from the live registry on every request; both are pinned by tests, including that a manual added between two requests is in the second one’s answer.

**Applying a change request now announces the tree it rewrote.** This was the one commit path that did not invalidate anything, and an approved `.tool` or `SKILL.md` could stay invisible — to every open MCP connection and every browser — for tens of seconds after it landed. `mergePr` runs `git merge --no-ff` in the target branch's own workspace and pushes, so the pull that follows is a no-op: `treeChanged` is false and `pullWorkspace` announces nothing, because it announces a pull that moved the tree and this one did not — the merge did. Nothing else covered it: `change-request-merged` carries no branch and no workspace, so the catalog subscriber cannot act on it, and a later `POST /api/sync/<branch>` answers "up-to-date" without pulling for the same reason. A merge into the default branch now emits `fs-tree-changed` for the workspace it rewrote, unless the pull already did.

**The local server checks while it is in use, and never while idle.** The catalog check runs on activity — a tool call finishing, a client listing the tools, where a listing waits for its check so the list handed back is the current one — and on nothing else. An idle connection asks the workspace nothing AND holds nothing open: no timer, and no socket parked per laptop, so a laptop nobody is using costs the deployment nothing and fifty of them cost it nothing together. It catches up at its next use, which is the first moment a stale toolset would have cost it anything. The throttle that collapses a burst onto one digest read is two seconds, counted from when a check STARTS rather than when it settles: it is also the ceiling on staleness for a connection in use, since a check landing just before a commit reads the old catalog and opens a fresh window, and at five seconds — the ceiling this replaces — that alone put the first sighting at ~7.6s against a deployment that had the manual in about one. Two seconds leaves the rest of that budget for the digest read and the ~2.4s re-registration a change costs. The idle contract is pinned by a test that counts every request the local server makes on any path, and every one the deployment is still holding, so neither a timer nor a held socket can come back unnoticed.

The local server registered the deployment's manuals once, at startup, so a tool committed afterwards stayed invisible until someone restarted the process. It now compares a new `GET /api/agent/catalog-revision` — a per-caller fingerprint of the tool manuals and skills the caller may read, ACL-filtered by the same services the listings use — and on a change re-registers everything it holds: the deployment's manual and every local-only server (`local: true`, or a `type: "stdio"` command), which is fetched to disk again and whose child process the re-registration restarts. Then it sends the MCP tool-list-changed and prompt-list-changed notifications, declaring both `listChanged` capabilities so a client knows it may trust the list between them. `/api/config` advertises the route as a `catalogRevision` capability, the same mechanism agent instructions use and for the same reason: an unknown `/api/*` path on an older deployment falls through to the JWT mounts and answers 401, so a probe would tell the user to mint a new connection key over a route that is merely not there. An older deployment says so once on stderr and keeps its startup toolset. The one thing that can delay a refresh: it waits for a tool call that is still running before it re-registers, for up to fifteen seconds, so a commit made mid-call lands once that call finishes — and a call that outlasts the wait has the re-registration happen underneath it, because one wedged call must not hold the toolset stale for as long as it cares to run.

`list_skills` and `get_skill` no longer disagree about the same skill. The listing resolved read access through the batch gate, which memoizes a file's own frontmatter rules per workspace, while loading by name resolved it through the single-file gate, which reads disk on every call — so a freshly written `SKILL.md` could be loadable by name and absent from the listing, and an author who wrote a skill and then listed them did not see their own work. Both now resolve through the one gate — and that gate is dropped on the same default-branch signal that drops the catalogs, so the listing and the load are refreshed by one event or by neither.

`AGENTS.md` states the five-second timeframe for a connection in use, says plainly that an idle one is told nothing and holds nothing open and catches up at its next use, names the change-request path alongside the app, the file tools and a git push, and keeps the caveat the timeframe depends on: a client that caches the list it was given at connect time, rather than honouring the notification, must re-list or reconnect.
