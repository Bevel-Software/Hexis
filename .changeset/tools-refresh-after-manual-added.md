A tool manual or skill added, changed or removed on the default branch is live within five seconds, on the connection you already have and without a reconnect — whether or not anyone was using that connection when the commit landed. A skill is in the very next `list_skills` or `get_skill` on either connection, because skills are read from the workspace on every request. A commit touching a `.tool`, an `mcp.json`, a `plugin.json` or a `SKILL.md` drops the released catalogs whichever path made it, and the hosted endpoint, being stateless, already rebuilt its tool surface from the live registry on every request; both are pinned by tests, including that a manual added between two requests is in the second one's answer.

**Applying a change request now announces the tree it rewrote.** This was the one commit path that did not invalidate anything, and an approved `.tool` or `SKILL.md` could stay invisible — to every open MCP connection and every browser — for tens of seconds after it landed. `mergePr` runs `git merge --no-ff` in the target branch's own workspace and pushes, so the pull that follows is a no-op: `treeChanged` is false and `pullWorkspace` announces nothing, because it announces a pull that moved the tree and this one did not — the merge did. Nothing else covered it: `change-request-merged` carries no branch and no workspace, so the catalog subscriber cannot act on it, and a later `POST /api/sync/<branch>` answers "up-to-date" without pulling for the same reason. A merge into the default branch now emits `fs-tree-changed` for the workspace it rewrote, unless the pull already did.

**The workspace announces a catalog change; the local server no longer has to be asked.** Activity-driven checks answer for a connection in use and say nothing to an idle one — and the criterion is about a person who commits a `.tool` and waits, which is exactly the idle connection. A heartbeat covers that and was taken out twice for a reason that has not changed: two seconds per idle laptop is a load that scales with laptops, and fifty of them would ask a deployment the same question all day for nobody. So the deployment speaks instead. A new `GET /api/agent/catalog-events` streams the caller’s catalog fingerprint — the same per-caller, ACL-filtered digest `/api/agent/catalog-revision` answers — writing one event when the stream opens (which closes the gap between a bridge’s startup discovery and its subscription) and one more each time that fingerprint actually moves. It is fed by the very invalidation that drops the catalog caches, so the push and the caches can never disagree about what a change is, and it announces nothing when the fingerprint did not move: the signal behind it fires on ANY default-branch write, and an ordinary note would otherwise re-register every connected laptop’s toolset. An idle connection now costs one parked socket and hears about a commit in the moment it lands; the activity checks stay exactly as they were, as the fallback for a deployment too old to advertise the stream or a proxy that will not carry it, and the two-second from-start throttle still collapses a burst onto one digest read.

The local server registered the deployment's manuals once, at startup, so a tool committed afterwards stayed invisible until someone restarted the process. It now compares a new `GET /api/agent/catalog-revision` — a per-caller fingerprint of the tool manuals and skills the caller may read, ACL-filtered by the same services the listings use — and on a change re-registers everything it holds: the deployment's manual and every local-only server (`local: true`, or a `type: "stdio"` command), which is fetched to disk again and whose child process the re-registration restarts. Then it sends the MCP tool-list-changed and prompt-list-changed notifications, declaring both `listChanged` capabilities so a client knows it may trust the list between them. `/api/config` advertises the route as a `catalogRevision` capability, the same mechanism agent instructions use and for the same reason: an unknown `/api/*` path on an older deployment falls through to the JWT mounts and answers 401, so a probe would tell the user to mint a new connection key over a route that is merely not there. An older deployment says so once on stderr and keeps its startup toolset. The one thing that can delay a refresh: it waits for a tool call that is still running before it re-registers, so a commit made mid-call lands once that call finishes.

`list_skills` and `get_skill` no longer disagree about the same skill. The listing resolved read access through the batch gate, which memoizes a file's own frontmatter rules per workspace, while loading by name resolved it through the single-file gate, which reads disk on every call — so a freshly written `SKILL.md` could be loadable by name and absent from the listing, and an author who wrote a skill and then listed them did not see their own work. Both now resolve through the one gate — and that gate is dropped on the same default-branch signal that drops the catalogs, so the listing and the load are refreshed by one event or by neither.

`AGENTS.md` states the five-second timeframe again — it holds for an idle connection now, which is what it could not honestly say while activity was the only trigger — names the change-request path alongside the app, the file tools and a git push, and keeps the caveats it depends on: a client that caches the list it was given at connect time, rather than honouring the notification, must re-list or reconnect; and where the stream cannot be held open at all, the five seconds becomes the connection’s next use.
