Agents read history and sync their drafts with tools, not a shell. Five tools join the workflow tools, on the internal and the external catalog alike: `list_file_changes` (a file's commits — who, when, subject — as the History tab shows them), `read_file_at` (the file at a commit on the branch's own history, with the version just before it, or at another branch's published tip), `compare_file` (the diff of one commit, or of a file between two branches), `branch_status` (ahead/behind, whether the shared branch moved, files written but not committed, the fork base and the paths a change request would carry) and `update_branch` (bring the draft's target, or the draft's own shared state, into the draft as a merge commit by the caller, and publish it). Every read is subject to the same per-file access checks as the existing file and history routes: the caller's read permission on the workspace's own branch, and, for content from another branch, the permission at the very commit the content was served from (pinned by the read itself, never a branch ref a fetch may move; a commit whose rules cannot be read grants nothing) — the rule the app's compare route now takes too. A deployment's agent read hook is told of each read, as it is of `read_file`. Path lists show only the paths the caller may read.

`update_branch` is how an agent resolves conflicts. A conflicted merge is never left on disk: the first call describes every conflicted path — the file at the merge base, on each side, and the working copy with git's markers — and undoes the merge in the same reservation; a second call, with the same `from` and a resolution per conflicted path (the resolved text, or one side kept whole, byte for byte, or the file deleted), lands the merge for real and publishes it before the reservation is released, through the same cooperative recovery every workflow push takes (a replay that conflicts, or a host that refuses, answers as every refused share does: the caller gets the saved-locally hand-off naming the branch and no conflicted path, and the branch's sync banner names the files, as it does for every pull conflict). A resolution naming a path that is not conflicted is refused before anything is written, so the only edits that bypass the file tools' locks are the conflicts themselves. A side that is binary or very large is left out and named in `truncated`, to be read where it lives (the draft's own file with `read_file`, the merged-in branch's with `read_file_at` at that branch, the base's at the merge base). A conflicted file the caller may not read on one of the two branches is left out by name and only counted; it is not theirs to settle, however it would be settled, and a resolution takes the same draft write rule every save takes, decided inside the merge against the source commit actually merged. Every read also goes through a deployment's agent read hook. A protected branch is never updated this way.
