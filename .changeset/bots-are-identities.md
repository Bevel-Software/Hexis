A bot is an identity of its own. It is a users row marked as a bot, with the address `<id>@agent.hexis` (an admin may change the domain), granted and denied access by that address like a person and through the groups it is in. It is not part of "everyone", holds no role, is never an admin, never signs in, is never mailed, and cannot change access: its writes to `roles.yaml`, an `access.md`, a group file or a file's own access lines are refused (through every file tool, `unzip` included), so is its deletion of an access file or of a file whose definition carries access lines (or its move of one away), and so is its merge of a change request that changes any of them.

The connection-key dialog and the sign-in consent step offer "Connect as": Myself, then each bot the person may act as (only who may write what defines the bot). A connection made as a bot acts as the bot's row on every call, with the bot's secrets and tool sign-ins, re-checked every call; when the bot cannot be used or its maker may no longer act as it, the connection loads nothing and says why. The audit log, a bot's commits (a `Made-by:` trailer), the change requests it opens and the merges it makes name the person beside the bot. The Secrets and Connect tools pages can be opened for a bot by a link naming it; a managed connector (one connected through the distribution's broker) cannot be connected for a bot yet. A connection key made as a bot is refused by the marketplace git remote and the GitHub-facade API, which serve a person their own skills. A connection made as a bot is also offered two agent tools, `approve_change_request` and `apply_change_request`, which approve and apply a change request through its own gate where the bot is granted (applying also needs the bot to be able to write every file the request changes); a connection made as Myself is never offered them, and the person applies in the app as before.

Changing the bots' domain gives every bot its new address at once and opens one change request that rewrites every grant naming a bot at the old domain: in every `access.md`, `roles.yaml`, group file and file definition (`.md`, `.tool`), found the way the access model finds them, so files `.bevelignore` hides from the explorer are rewritten too; a folder that cannot be listed refuses the change request rather than opening a partial one. Until it is merged a grant at the old domain still counts, and the domain cannot be changed again while it is open. `start_session`'s `connectedAs` is the bot a connection was made as (its address as `path`, and its name), null for Myself.

Breaking for a distribution: `CorePorts.agentScope` (an agent configuration that narrowed a person's connection) is replaced by `CorePorts.bots`, a bot directory (`IBotDirectory`: the definitions, who may act as each, the platform tools it is offered, and the bot a legacy agent path stands for). A distribution must move to it with this version. A plugin that hosts its own tool endpoint passes `identities` (the same provider the hosted middleware takes) to `createToolValidator`, which now requires it. Core alone supplies no bot and behaves as before. Connections made "as an agent" before this keep working as that bot when the distribution maps the path to one and their owner may act as it; connections made as Everything are made as Myself. A key-mint or consent request that still names its choice as `agentPath` is refused rather than made as Myself.

For every agent, not only a bot: `unzip` writes each extracted file under that file's lock, with the write check asked again there, so a file someone holds open past the lock retries is skipped with the reason instead of overwritten, the no-link and git-folder checks are asked again at the moment each file lands, and a write that fails on disk fails the request instead of reading as a skipped file (the extracted files still stay uncommitted); and `move_file` of a folder without link rewriting takes the lock of every file it carries at both ends and lands as one change, as a move with link rewriting already did.
