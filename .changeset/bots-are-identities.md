A bot is an identity of its own. It is a users row marked as a bot, with the address `<id>@agent.hexis` (the domain is fixed; no setting changes it), granted and denied access by that address like a person and through the groups it is in. It is not part of "everyone", holds no role, is never an admin, never signs in and is never mailed. It changes access as any account does: its writes to an `access.md`, a group file or a file's own access lines, and its merges that change them, are judged by its own grants, the write gate of a protected branch and change-request approval. `roles.yaml` stays admin-only, so a bot never writes it. A bot has one extra condition, on merging a change request: it may merge only where it may write every file the merge changes, since nobody else's approval stands in for its own grants.

The connection-key dialog and the sign-in consent step offer "Connect as": Myself, then each bot the person may act as (only who may write what defines the bot). A connection made as a bot acts as the bot's row on every call, with the bot's secrets and tool sign-ins, re-checked every call; when the bot cannot be used or its maker may no longer act as it, the connection loads nothing and says why. The audit log, a bot's commits (a `Made-by:` trailer), the change requests it opens and the merges it makes name the person beside the bot. If that person's account is erased while a bot's request, approval or merge is being recorded, one of two things happens in the database: the record lands first and the erasure anonymizes it with the rest, or the erasure lands first and the call is refused without naming them. Such a call that waits more than five seconds for an erasure to finish is refused as busy and can be tried again. A bot's save is never refused for that person, because its bytes are already written: a save still queued when the erasure runs is anonymized with the rest, but one the worker had already picked up, or one queued after the erasure finished, can still name them in its commit's `Made-by:` trailer. An erasure never rewrites git history. The Secrets and Connect tools pages can be opened for a bot by a link naming it; a managed connector (one connected through the distribution's broker) cannot be connected for a bot yet. A connection key made as a bot is refused by the marketplace git remote and the GitHub-facade API, which serve a person their own skills. A connection made as a bot is also offered two agent tools, `approve_change_request` and `apply_change_request`, which approve and apply a change request through its own gate where the bot is granted (applying also needs the bot to be able to write every file the request changes); a connection made as Myself is never offered them, and the person applies in the app as before.

`start_session`'s `connectedAs` is the bot a connection was made as (its address as `path`, and its name), null for Myself.

Breaking for a distribution: `CorePorts.agentScope` (an agent configuration that narrowed a person's connection) is replaced by `CorePorts.bots`, a bot directory (`IBotDirectory`: the definitions, who may act as each, the platform tools it is offered, and the bot a legacy agent path stands for). A distribution must move to it with this version. A plugin that hosts its own tool endpoint passes `identities` (the same provider the hosted middleware takes) to `createToolValidator`, which now requires it. Core alone supplies no bot and behaves as before. Connections made "as an agent" before this keep working as that bot when the distribution maps the path to one and their owner may act as it; connections made as Everything are made as Myself. A key-mint or consent request that still names its choice as `agentPath` is refused rather than made as Myself.
