An agent lands files on a branch by uploading them, so their content never passes through the model.

`request_file_upload` answers a one-time upload address, the token that authenticates it, the expiry and the deployment's size limit. The agent POSTs one file — or one zip holding many — to that address with any HTTP client, and the answer names what arrived: the file name, its size, and for a zip how many entries it holds. The token may travel either in that address’s last path segment or in an `x-upload-token` header sent to the address without it, so a caller whose command lines are logged or shared need not put its credential in a URL. The bytes are stored beside the workspaces root, outside every workspace, where no file tool can name them. `apply_file_upload` then takes the token, a branch, a destination folder and a `mode`, and lands the content there in one commit as the calling user: a single file under the name it was sent with, a zip as its entries with their folder structure. `mode` means what it means on `write_file` — `create` (the default) refuses a path that already exists, `overwrite` replaces, `update` refuses a path that does not — and the answer names every path with its outcome (`created`, `replaced`, `updated`, or `refused` with the reason), cut to 25 entries with the total unless the caller asks for all. A refused path does not stop the others.

Every path is judged at apply time by the caller's write access and by the platform-file rules, as `write_file` judges it: on a protected branch the caller cannot write, nothing lands and the refusal names the change-request route; an entry whose own path is denied is refused on its own while the rest land; and an entry named `access.md`, `roles.yaml`, `.bevelignore` or the agent guide is refused, because those are configuration the platform reads and their writes are checked elsewhere. A zip entry that would land outside the destination, that is a symbolic link, that goes through a link already on disk, or that names the git folder is refused as `unzip` refuses it — the entry-name rules now live in one place both surfaces read. An apply runs in its destination folder’s turn, the one an explicit folder delete takes, so a folder delete can never remove the folder out from under files an apply has just reported landing. Text and binary land byte for byte: a PNG and a markdown file full of backslashes, quotes and unicode escapes keep the checksum they were uploaded with.

A token is single-use, bound to the user it was issued to, and short-lived: used twice, expired, or presented by somebody else, it meets one refusal that says which of those it was — none of them. Two uploads sent against one token at the same time meet it too, so a token accepts exactly one file. An upload whose token expires while its body is still arriving is refused too, rather than answered as received against a token nothing can be applied with. An upload nobody applies is deleted when its token expires, and an upload over the deployment's own limit is refused when it is sent, naming the limit; the token is judged before anything else about the request is read, parsed or quoted back, so an invented one costs nothing and learns nothing. Both tools are write tools, so a read-only deployment refuses them and no upload lands while it lasts — the raw upload route still accepts the bytes of a token issued earlier, which commit nothing and are deleted when that token expires. `AGENT_UPLOADS_ROOT` can move the staging directory, and a value inside `WORKSPACES_ROOT` — or one that resolves there through a link — now refuses to boot rather than staging unjudged bytes where the file tools read. The descriptions of `write_file`, `write_files` and `edit_file` now name this route in one sentence as the way to land large, escape-heavy and binary content, and why and how is one of the rules every file tool shares, in the handshake instructions and in the agent guide.

An upload is written to disk as it arrives and never held in memory, and one user may hold at most ten tokens open at once: an eleventh `request_file_upload` is refused with a 429 until one is applied or expires. The tokens are one process's memory, so a restart ends the ones that were open; and a staged file a process has no record of is left alone until it is older than any token could still be good for, so two processes over one staging directory — the old and the new during a restart — never delete each other's uploads.

**A zip entry is never inflated past what may land, whatever its header declares — in `apply_file_upload` and in `unzip`.** An archive reader caps an inflation at the size the entry's header declares, but only when that size is above zero. An entry declaring zero passed the size check and was then inflated with no cap at all: 20 KB expanded to 20 MB, and an archive at the upload limit to tens of gigabytes in a single call. `unzip` has read entries in that order since it was written, so this closes it there too. Both now read through one bounded reader: an entry declaring more than what is left of the limit is refused unread, one declaring an empty file is inflated capped at a single byte (a file that really is empty still lands), and a read that fails — a failed checksum, a stream longer than it declared — is that entry's refusal rather than the whole archive's.
