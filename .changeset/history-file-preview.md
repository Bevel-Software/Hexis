Version history now shows a past save of a document, an image or an HTML page with the viewer the file page uses for that format, instead of the `git show` patch every non-markdown file got. Selecting last week's save of `Q3-report.pdf` shows that PDF's pages; an older `logo.png` shows the picture as it was; `memo.docx`, `deck.pptx`, `budget.xlsx`, `request.eml` and `landing.html` each show their own. Before this, a PNG's or a PDF's history was git's one-line "Binary files a/… and b/… differ". The pane is headed "As saved &lt;when&gt; by &lt;who&gt;", is read-only throughout, and offers "Download this version" on any save that holds a version of the file — which is how an old version is recovered until Restore exists (now tracked in `TODOS.md`).

For `html`, `htm`, `csv` and `svg` the pane keeps the line diff behind a "Source changes" toggle, with "Preview" back. A format with no viewer (`doc`, `ppt`, `xls`, `odt`, `odp`, `ods`, `zip`, or any other binary — git's own word for it decides) shows "No preview for this format." and the download. A listed save that turns out not to have touched the file keeps the panel's own "No file changes in this save." — there is no version of it to preview or to download. The save that DELETED a file shows "This save deleted the file." with the version from just before it. A text format nothing renders (a `.txt`, a `.json`, a tool definition) keeps today's line diff, and a markdown file's history is exactly as it was: the rendered before/after diff, with its images still named rather than shown.

`GET /api/workspace/:id/file/raw` takes `?ref=<sha>` (and `&side=before` for the version just before that save) and serves those bytes verbatim — a downloaded past version has the checksum of what was uploaded. Everything around the read is unchanged: the same `read:` gate, the same `download:` verb, the same content type, the same SVG sandbox. Both gates resolve against the file's rules TODAY, so anyone who may read a file may open any of its past saves and anyone who may not is refused as they are for the file itself; the rules as they were at the save play no part. A malformed `ref` is a 400 and never falls back to the working tree, and the ETag is the blob's own id, so a revisited version costs a revalidation rather than the bytes.

Every read of a past save is now scoped to the branch being viewed: a sha that is not in that branch's history — one from someone else's branch, or an invented one — is refused with 404 "This version is not in this file's history on this branch." This applies to the new byte route AND to the existing `workflow/show-file` and `workflow/file-at-change` routes, which previously served any sha the repository happened to contain. A save the history panel lists is never refused this way.

`IWorkflowService` gains `fileBytesAtChange(workspaceId, path, sha, side)`; any other implementation of that interface must add it. The six document viewers (`PdfRenderer`, `DocxRenderer`, `XlsxRenderer`, `PptxRenderer`, `EmailRenderer`, and `ImageRenderer`) now offer "Try again" beside a failed read wherever they are mounted, the file page included — previously only the image viewer did, and a dropped connection left the others on their error until something remounted them. The viewers stay lazily loaded: no viewer moves into the eager bundle. Pressing "Try again" unmounts the button itself, so it hands keyboard focus to the pane it sits in — the file page, Version history and the change-request dialog each mark their viewer host as that region — instead of dropping focus to the page and sending the next Tab back to the top.

A workspace path carrying a control character is now refused with a 400 wherever one enters — at `normalizeWorkspacePath`, which every route and MCP tool goes through, and at the pathspec validator every path handed to git passes. A line break was the one that mattered: `git cat-file --batch` reads one `<ref>:<path>` object name per LINE, so `Docs/secret.md%0Azzz` named one thing to the access gates — a file that exists nowhere, so the real file's own frontmatter rules were never consulted — and two things to git, which answered about `Docs/secret.md` and served its bytes. A reader of a folder who is denied one file inside it by that file's own rules could read it that way, and in the access resolver's batch read the extra answer shifted every result after it, so one directory was judged by another's `access.md`. Both `--batch` readers now also refuse a spec that is not one line, as a fence at the protocol. No real file name is affected: the shared filename validator has always refused this range per segment. The checkout folder name is held to the same rule, since every workspace path is prefixed with it: `KB_DIR_NAME` carrying a control character now fails the boot with a message naming the setting, and the `kbDirName` setting refuses one on save. A deployment whose folder name is an ordinary name is unaffected.
