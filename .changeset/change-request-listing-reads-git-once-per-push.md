A change-request listing starts no git process for what it has already read: where a branch tip points comes from the repository's own ref files (the loose ref, or `packed-refs`, a symbolic ref followed, a worktree's shared refs included) instead of a `git rev-parse` per tip, and git is asked only for what the files cannot decide, such as a tag or a repository whose refs live in a reftable. The files a request changes are read from git once per pair of commits and remembered under that pair for the life of the process: a push moves a tip, the pair changes, and that one request is diffed again; a restart, or a pair evicted from the bounded memo, reads it once more. The own access entries of a path at a commit are remembered the same way, so the access gates a listing runs at every open request's two refs read each path once per commit. On a knowledge base with a hundred open requests a listing started three to four git processes per request on every read; a listing that has seen its requests before now starts none until someone pushes.
