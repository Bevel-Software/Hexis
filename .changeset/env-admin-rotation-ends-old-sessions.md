Rotating the deployment admin's `ADMIN_PASSWORD` and restarting now ends every session that account opened with the old password: each such token and browser session answers 401 with the same "Your password was changed after this session was opened" message a stored-password change gives. That answer, and the one for a switched-off account, now come in the same words from every route that takes a session as its bearer: before, the MCP endpoint and the agent manual routes answered a session a password change ended with "Invalid or expired token" (the agent manual routes answered a switched-off account the same way), and remote sync (`/api/sync`) answered either as a wrong credential: 401 "A valid sync secret or an administrator session is required", or, when no sync secret is configured, 503 asking for one. The deployment admin's account keeps a stamp of the `ADMIN_PASSWORD` its sessions belong to (new column `users.env_admin_stamp`: an HMAC keyed with `JWT_SECRET`, never the password itself). Each boot compares it with the current password and, when they differ, moves that account's session generation on, which ends every session it opened before, by password or through single sign-on. Each rotation is a new generation, so setting `ADMIN_PASSWORD` back to an earlier value does not revive that value's sessions. A restart that leaves `ADMIN_PASSWORD` unchanged keeps the sessions. During a rolling restart, a process still running under the old password stops accepting it once a process under the new password has booted. The first boot of this version moves the deployment admin's generation on once, so it signs in again after upgrading. Unsetting `ADMIN_PASSWORD`, or moving `ADMIN_EMAIL` to another address, ends the former deployment admin's sessions the same way. Other accounts are unaffected.
