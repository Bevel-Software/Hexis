Rotating the deployment admin's `ADMIN_PASSWORD` and restarting now ends every session that account opened with the old password: each such token and browser session answers 401 with the same "Your password was changed after this session was opened" message a stored-password change gives. That answer, and the one for a switched-off account, now come in the same words from every route that takes a session as its bearer: before, the MCP endpoint and the agent manual routes answered a session a password change ended with "Invalid or expired token" (the agent manual routes answered a switched-off account the same way), and remote sync (`/api/sync`) answered either as a wrong credential: 401 "A valid sync secret or an administrator session is required", or, when no sync secret is configured, 503 asking for one. The deployment admin's session token carries a stamp of the `ADMIN_PASSWORD` it was issued under, and the account keeps the stamp of the current one (new column `users.env_admin_stamp`); each stamp is an HMAC keyed with `JWT_SECRET`, never the password itself. A process accepts the deployment admin's session only when it carries the stamp of the password that process runs under. So while processes under the old and the new password run side by side (a rolling restart), each accepts only the sessions opened under its own password, and once every process runs the new one, no session opened under the old one is accepted, whether it was opened by password or through single sign-on. Each boot also compares the account's stamp with the current password and, when they differ, moves the account's session generation on, so setting `ADMIN_PASSWORD` back to an earlier value does not revive that value's sessions. A restart that leaves `ADMIN_PASSWORD` unchanged keeps the sessions. The deployment admin signs in again after upgrading, since tokens issued before this version carry no stamp. The sessions the deployment admin opens under this version also end when `ADMIN_EMAIL` moves to another address (moving it back does not revive them), and when `ADMIN_PASSWORD` is unset, which a deployment can do only with password sign-in switched off (`LOGIN_PASSWORD=false`). Other accounts are unaffected.
