The page tool bridge is one controller every HTML renderer calls. `useHtmlToolBridge({ iframeRef, filePath, viewKey })` owns what answers a page's `window.bevel.tools` and `requireTools()` — which pages get tools (the app's file page, never a surface), the viewer's tool client, the per-view consent, the two cards and the frame's tool messages — and hands back `{ toolBridge, cards }`: the renderer builds its frame's document with `toolBridge` and renders `cards` beside it. Core's `HtmlRenderer` is its first caller and keeps no bridge code of its own; a distribution's own `.html` renderer gets the same behaviour by calling it. The renderers module's entry (and workspace's) now exports `useHtmlToolBridge`, `PageToolsContext`, `OpenPageInPlatformContext` and their types (`HtmlToolBridgeOptions`, `HtmlToolBridgeResult`, `PageTools`), so no renderer, host or test of the app reaches `htmlToolBridge.ts` from outside the module (the browser fixtures under `browser/`, which drive the file itself, still do).

Each view's document carries an identity the controller minted for it (`buildSandboxedHtml`'s `toolBridge` takes `{ documentId }`, and the frame runtime stamps it on every message), so the app answers only the document it built: a message a replaced document queued before a view change and the frame's window delivered after it is ignored. A call made in a view that has ended before it was decided — the lookup of whether the tool writes still in flight, or its consent card still open, when the page is reloaded, saved, changed under the viewer or switched to Edit — is now answered `closed`, opens no card in the next view, and runs nothing, even after an Allow the ended view gave. Before, the lookup's late answer could open the consent card in the new view for the old call, and on Allow run it against the server.
