Adding a file where you will not be able to see it now says so first, and a proposed row opens its change request at the file you clicked.

When something is created at a spot its creator cannot read, the platform keeps it visible to them by writing a creator `read:` grant — into the topmost new directory's `access.md`, or, for a loose file dropped into a folder that already exists, into the file's own frontmatter. Only markdown carries frontmatter. So a non-markdown file landing directly in an existing folder the creator cannot read gets no grant at all: the backend logs it and carries on, and the file vanishes from the very person who just proposed it. That is a legitimate thing to want — the change request still reaches the folder's owners — so the platform does not refuse it. It asks: "You won't be able to see &lt;name&gt; after it is added: you don't have read access to &lt;folder&gt;.", with Continue and Cancel, and Cancel creates nothing at all.

One gate serves the sidebar's new-file box, the drop targets and the upload buttons, so a multi-file batch asks exactly once and lists the affected names. The two conditions mirror the backend's grant decision rather than approximating it: markdown never asks, and neither does anything landing under a subfolder of the drop, because a new directory carries the grant in its own `access.md` whatever goes in it. A new folder never asks for the same reason. The read verdict comes from the server's own resolver (`GET /access?kind=folder`), never from the tree — the tree shows folders you can see, and the question is about one you cannot. A lookup that fails lets the creation through: the warning is a courtesy, and no courtesy is worth blocking a creation the server would have accepted.

A proposed row — a file that exists only on your own suggestions branch — used to open the shared change-request dialog on whatever file the request happened to list first. On a bundle of twenty proposals that is a different document from the one that was clicked. The dialog now takes the file to land on, selects it in its file tree and shows its diff. Which request and which file both live in the URL (`?cr=12&file=knowledge-base/Sales/brief.pdf`), so a reload — or a link pasted to a colleague — arrives at the same file of the same request, and closing the dialog clears them again.
