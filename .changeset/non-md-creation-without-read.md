Adding a file where you will not be able to see it now says so first, and a proposed row opens its change request at the file you clicked.

When something is created at a spot its creator cannot read, the platform keeps it visible to them by writing a creator `read:` grant — into the topmost new directory's `access.md`, or, for a loose file dropped into a folder that already exists, into the file's own frontmatter. Only markdown carries frontmatter. So a non-markdown file landing directly in an existing folder the creator cannot read gets no grant at all: the backend logs it and carries on, and the file vanishes from the very person who just proposed it. That is a legitimate thing to want — the change request still reaches the folder's owners — so the platform does not refuse it. It asks: "You won't be able to see &lt;name&gt; after it is added: you don't have read access to &lt;folder&gt;.", with Continue and Cancel, and Cancel creates nothing at all.

One gate serves the sidebar's new-file box, the drop targets and the upload buttons, so a multi-file batch asks exactly once and lists the affected names. The two conditions mirror the backend's grant decision rather than approximating it: markdown never asks, and neither does anything landing under a subfolder of the drop, because a new directory carries the grant in its own `access.md` whatever goes in it. A new folder never asks for the same reason. The read verdict comes from the server's own resolver (`GET /access?kind=folder`), never from the tree — the tree shows folders you can see, and the question is about one you cannot. A lookup that fails lets the creation through: the warning is a courtesy, and no courtesy is worth blocking a creation the server would have accepted.

A proposed row — a file that exists only on your own suggestions branch — used to open the shared change-request dialog on whatever file the request happened to list first. On a bundle of twenty proposals that is a different document from the one that was clicked. The dialog now takes the file to land on, selects it in its file tree and shows its diff. Which request and which file both live in the URL (`?cr=12&file=knowledge-base/Sales/brief.pdf`), so a reload — or a link pasted to a colleague — arrives at the same file of the same request, and closing the dialog clears them again.

The ticket's investigation reproduced two defects in the change-request flow against a running instance, and both are fixed here.

**Proposing again while the first proposal is still loading no longer fails.** Two files dropped back to back produced `An open change request already exists from "suggestions/…" to "main" (#2)` on the second — shown as "Couldn't add change request". Both flows had read "no open request of mine" from the same fresh list and both went on to open one. The window is exactly how long that list read takes, and it grows with the number of open requests. Two halves, both closed: concurrently, the second proposal now joins the first's open instead of issuing its own, so only one request is ever in flight per branch; and sequentially — or from another tab, or another device, where nothing on the client can see the other flow — the server's duplicate refusal is read for what it is. It names the request that already exists, which is the state the proposal was trying to reach, so it is adopted instead of failing. The fresh list read is deduplicated the same way, so two proposals started together pay for it once. Both are in-flight only and never a cache: whether you still have an open request is the server's answer to give.

**The change-request list no longer pays a network round trip per open request.** Every summary needs the request's touched paths, and computing them fetched the two refs that request is about before diffing them — once per open request, on a list that is re-read after every proposal and polled every 60 seconds, with the tree asking two list endpoints at once. A cold list measured 1.31s at two open requests and 3.48s at five, about 0.55s more for each one added. The list now refreshes the whole clone once (`git fetch --prune origin`, already sharing an in-flight fetch between callers) and diffs locally against the refs that brings, so its cost stops growing with the size of the queue. Freshness is not traded away for it: a read that says it is fresh — the one fired because a proposal just landed — forces that refresh past its 30-second window, for the same reason it bypasses its own cache, and the touched-paths diff still fetches for itself when a branch is one this clone has never heard of. That last case is not a stale answer, it is no answer: an empty file list, which is a change request missing from its own author's tree. Every other caller of the diff — the request detail, the merge paths, the folder checks — keeps its own fetch, because none of them has just refreshed the clone.

The third reported symptom, "the request is not visible to its submitter", did not reproduce with read permission present: an extensionless file and its `.md` twin, proposed from the repository root and from a readable subfolder, were all in the tree and in the submitter's own request list after a full reload. Nothing was changed for it.
