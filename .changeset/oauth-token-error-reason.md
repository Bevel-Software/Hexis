A sign-in that the provider's token endpoint refuses now says why, in the log and on the Connect page. The error carried only the HTTP status ("Token endpoint returned HTTP 400"), so neither could tell a client the provider does not accept from a refused authorization code. The message now names the provider's error code (`invalid_client`, `invalid_grant`, or a provider's own code such as `BAD_CLIENT_SECRET`) and adds Hexis's own sentence for it: for `invalid_client`, that the client id or client secret this sign-in uses is not accepted and the tool owner should check the declared client id and set the client secret again; for `invalid_grant`, that the grant was refused (for a sign-in a redirect URL mismatch or an expired or reused code, for a refresh an expired or revoked refresh token) and to sign in again. The codes are a finite list (the OAuth ones and HubSpot's own status codes); a code outside it is not shown. Nothing else of the provider's response is ever quoted, so no secret can reach a log or a page through it. The Connect page lands with "Authorization failed." followed by that message; a failure that is not the provider's refusal keeps the generic line. The callback route's "oauth callback failed" log line carries the same message, and a refresh the provider refuses now logs what it did (the sign-in wiped, or kept because a concurrent refresh had rotated it, or nothing wiped because the row had been replaced), which until now left no trace. The connection probe's capped response reader moves to `shared/read-capped.ts`, where the vault reads refusals through it too.
